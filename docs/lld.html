Low-Level Design

A metrics service that computes total revenue collected over an arbitrary date range across multiple sources, from one canonical definition, exposed through two views that agree by construction — with a CI mechanism that fails the build if a second implementation of the number ever appears. Stack: Node 20 · TypeScript (strict) · Express · postgres.js · Zod · Vitest · fast-check · Neon Postgres.

1Overview & the load-bearing rule

The invariant everything serves Exactly one component knows which statuses count as collected, and every read path goes through it. That component is the collected_revenue() SQL function, parameterised by COLLECTED_STATUSES — a constant declared once in metrics.definition.ts. No SQL string anywhere contains a canonical status literal.

Ingestion writes raw_status verbatim and never interprets it. Interpretation happens once, at read time, by joining to status_map. That separation is what lets a new source or a new status value arrive without touching the metric — adding a fourth source is a new folder plus rows in status_map; no file under metrics/ changes.

Why the definition lives in SQL. A Postgres function is the narrowest possible surface: both endpoints call it, no application code can bypass it without writing raw SQL against transactions.status, and that bypass is exactly what the anti-drift grep guard detects. A TypeScript-only definition would be equally valid but gives the enforcement test a fuzzier boundary.

Scope discipline No Kafka, no orchestrator, no hexagonal architecture — none is justified by this workload. An Express service, three tables and a genuinely good test suite reads as more senior than infrastructure the brief never asked for.

4Schema (DDL)

Full data model, field-by-field rationale, and the “why no foreign key” argument live in the ERD. The DDL, as it ships in migration 001:

create table transactions (
  id            bigserial   primary key,
  source        text        not null,
  external_id   text        not null,
  raw_status    text        not null,
  amount_minor  bigint      not null,
  currency      char(3)     not null,
  occurred_at   timestamptz not null,
  raw           jsonb       not null,
  ingested_at   timestamptz not null default now(),
  unique (source, external_id)
);

create table status_map (
  source     text not null,
  raw_status text not null,
  canonical  text not null
    check (canonical in ('collected','pending','failed','refunded','voided')),
  primary key (source, raw_status)
);

create table ingest_quarantine (
  id          bigserial   primary key,
  source      text        not null,
  payload     jsonb       not null,
  error       text        not null,
  created_at  timestamptz not null default now()
);

create index on transactions (occurred_at);
create index on transactions (source, raw_status);

unique (source, external_id) is what makes re-running a sync safe. raw is kept so a mapping mistake can be corrected without re-fetching from the provider. There is no FK from transactions to status_map — unmapped rows must be insertable so they can be reported as unclassified.

5The canonical definition

In one sentence Collected revenue for a range is the sum of amount_minor, grouped by currency, over transactions whose (source, raw_status) maps to a canonical status in COLLECTED_STATUSES, where occurred_at falls in the half-open interval [from, to) evaluated in the caller's timezone. COLLECTED_STATUSES is declared once in TypeScript and passed into SQL as a parameter.

The function both endpoints call (migration 002)

create or replace function collected_revenue(
  p_from      timestamptz,
  p_to        timestamptz,
  p_tz        text,
  p_bucket    text,
  p_collected text[]          -- passed in from metrics.definition.ts
) returns table (bucket_start date, currency char(3), amount_minor bigint)
language sql stable as $$
  select (date_trunc(p_bucket, t.occurred_at at time zone p_tz))::date,
         t.currency,
         sum(t.amount_minor)
  from transactions t
  join status_map m
    on m.source = t.source and m.raw_status = t.raw_status
  where m.canonical = any(p_collected)
    and t.occurred_at >= p_from
    and t.occurred_at <  p_to
  group by 1, 2
  order by 1, 2;
$$;

Two things are deliberate. The inner join means an unmapped status cannot match and therefore cannot be counted — the allow-list expressed structurally. And p_collected is a parameter, not a hardcoded literal, so the definition exists in exactly one place. The trade — a caller could pass a different array — is closed by the single-implementation guard, which asserts only metrics.repository.ts ever calls this function.

Edge-case rulings, decided once and written down

QuestionRulingReason
Are refunds netted out?The question doesn't arise — status is one field per row, so a refunded transaction leaves the collected set by exclusionGross-vs-net is only a debate when refunds are separate negative records
Partial refunds?Out of scope; named in the README as a known limitationStripe models these as separate refund objects this build does not ingest
Multiple currencies?Totals returned per currency; no conversionSumming INR and USD produces a number that is confidently wrong
Unknown status?Contributes zero, and is counted in unclassifiedFail closed, report loudly
Timezone?Caller supplies an IANA tz, defaulting to UTC; both views use the same valueMixed bucketing is the single most common source of drift
Where does the allow-list live?One TypeScript constant, passed into SQL as text[]A literal in both SQL and TS would itself be the second implementation the brief warns about

6Type design & exhaustiveness

metrics.definition.ts is the only permitted home for canonical status literals. Adding a canonical status here forces every handler to be revisited — because a compile error is a better reminder than a code review.

// metrics.definition.ts — the ONLY file allowed to name canonical status literals.

export const CANONICAL_STATUSES =
  ['collected', 'pending', 'failed', 'refunded', 'voided'] as const;

export type CanonicalStatus = typeof CANONICAL_STATUSES[number];

// The allow-list. Exactly one meaning counts as revenue.
// Do NOT re-declare 'collected' anywhere else — the E5-S3 guard greps for it.
export const COLLECTED_STATUSES: readonly CanonicalStatus[] = ['collected'];

export function assertNever(x: never): never {
  throw new Error(`Unhandled canonical status: ${x as string}`);
}

Every switch over CanonicalStatus ends in assertNever, so adding a sixth status makes tsc fail until every site is updated (E5-S4). pnpm typecheck runs in CI and blocks merge. A documented experiment in the README shows the compile break in action.

Shared parameter validation (one Zod schema, both metric routes)

// metrics.schema.ts
const RangeParams = z.object({
  from: z.string(),                        // ISO date/datetime
  to:   z.string(),                        // exclusive — the README says so
  tz:   z.string().default('UTC')          // validated against the IANA database
          .refine(isValidIanaZone, 'unknown timezone'),
  currency: z.string().length(3).optional()
}).refine(p => Date.parse(p.to) > Date.parse(p.from),
          { message: 'to must be after from', path: ['to'] });

const BreakdownParams = RangeParams.extend({
  bucket: z.enum(['day', 'week']).default('day')
});

to is exclusive; tz defaults to UTC and is validated; an invalid range where to <= from returns 400 with a readable message. The same parsed range feeds both views, so they are comparable by definition.

Summary response — a total, derived by folding the breakdown

GET /metrics/revenue/summary?from=2026-01-01&to=2026-04-01&tz=Asia/Kolkata

{
  "range": { "from": "2026-01-01T00:00:00+05:30",
             "to":   "2026-04-01T00:00:00+05:30", "tz": "Asia/Kolkata" },
  "definition": "collected",
  "totals": [ { "currency": "INR", "amount_minor": "4820000" },
              { "currency": "USD", "amount_minor": "129900" } ],
  "unclassified": { "count": 0, "pairs": [] }
}
Derived, not computed beside The summary handler calls the same repository function and folds the buckets; it issues no aggregate query of its own. A code comment states this is deliberate and must not be “optimised” into a separate query. That is the structural answer to “make sure both views always agree.”

Breakdown response — same envelope, buckets in place of totals

GET /metrics/revenue/breakdown?from=2026-01-01&to=2026-04-01&tz=Asia/Kolkata&bucket=week

{
  "range": { "from": "…", "to": "…", "tz": "Asia/Kolkata", "bucket": "week" },
  "definition": "collected",
  "buckets": [
    { "bucketStart": "2026-01-01", "currency": "INR", "amount_minor": "250000" },
    { "bucketStart": "2026-01-08", "currency": "INR", "amount_minor": "0" }
  ],
  "unclassified": { "count": 0, "pairs": [] }
}
  • Amounts are returned as amount_minor (a string, driver-safe for bigint) with an explicit currency — never a formatted string. Every derived representation is another place to drift.
  • Empty buckets are present with zero (filled by generate_series in SQL), so the series has no gaps and a consumer's own sum matches.
  • Every response echoes the applied from, to, tz and bucket, so a screenshot is self-describing.
  • unclassified is identical across both endpoints.

8Money & time handling

ConcernRule
Money storageInteger minor units in bigint. Never float, never a numeric that could be summed loosely.
Decimal parsingDecimal strings (1250.50) → minor units via string/decimal math. parseFloat(x)*100 is banned — it yields 125049.999….
bigint over the wirePostgres drivers return bigint as a string. The API emits a string amount_minor with a currency beside it; decided once, documented.
Range semanticsHalf-open [from, to) everywhere — >= from and < to. A midnight-boundary event is never double-counted.
TimezoneOne IANA tz parameter, applied in the repository only, identically to both views. date_trunc(bucket, occurred_at at time zone tz).
Gap fillinggenerate_series in SQL, under the same timezone logic as the aggregation — not in JavaScript.

9Anti-drift tripwires (Epic 5)

The brief's hardest clause asks for something that would catch a second implementation. The deliverable is a mechanism, not a convention. Four tests fail the build.

IDTripwireWhat it asserts
E5-S1Reconciliation property testfast-check over ~200 random ranges (multi-year, multiple timezones, day & week): Σ breakdown buckets per currency == summary total, strict integer equality, no tolerance.
E5-S2Mapping coverageThe except query returns zero rows — every (source, raw_status) in transactions exists in status_map. Failure lists the offending pairs.
E5-S3Single-implementation guardGrep scan: collected literal only in metrics.definition.ts; no canonical literal in any SQL string; provider words only in mappers/seed/tests; collected_revenue() called by exactly one module; no from transactions SQL outside src/metrics/.
E5-S4Type exhaustivenessEvery switch over CanonicalStatus ends in assertNever; adding a sixth status breaks tsc until all sites update. Runs in CI.

The demonstration that makes it land

Record the enforcement working, not merely present — three deliberate breakages, three tripwires firing, with real terminal output pasted into the README.

Breakage introducedTripwire that fires
Seed a disputed status without mapping itE5-S2 mapping coverage
Write a second summary query using sum() in a routeE5-S3 single-implementation guard
Bucket the breakdown in UTC while summary uses tzE5-S1 reconciliation
Honest about the tool The grep guard is intentionally crude, and the README says so. An AST/ESLint rule would be more precise, but a regex scan that runs in CI and fails loudly is a better trade at this scale than a custom plugin nobody reads. The property test runs against real seeded Stripe/Razorpay rows, so it proves timezone handling, not just arithmetic.

10Errors & resilience

  • A database error returns 503 with a correlation id (a per-request UUID, logged and echoed), never a stack trace.
  • Invalid parameters return 400 naming the offending field.
  • Ingestion from one source failing does not prevent the other two from completing; the ingest summary reports per-source outcome, including which source failed and why.
  • A record failing Zod validation goes to ingest_quarantine with its payload and error; the batch continues.
  • Structured logs carry source, counts and duration for each run.

The two questions a reviewer will ask

Why isn't the definition just a view? A view would fix the allow-list inside the database, putting the definition back in two languages. A parameterised function keeps one declaration and lets the guard test assert it.

What happens when a source renames a status? The old mapping stays, the new one is added, and historical numbers are unchanged because rows carry the raw status they arrived with. What this build lacks is validity-dating on the mapping — correcting a past mapping error would retroactively change a reported figure. That is the first thing to add in production.

15Out of scope & production notes

Deliberately out of scope

Authentication, pagination, caching, multi-tenancy, a UI, partial-refund modelling, and FX conversion. Each is named in the README so the omission reads as a decision, not an oversight.

What I'd add in production

  • Append-only status events with validity-dating on the mapping, so a corrected mapping doesn't rewrite history.
  • Alerting on a rising unclassified count — the early signal that a source added a status.
  • Dated FX rates with an as-of date, if a single converted total is ever required.
  • An AST-based lint rule replacing the grep guard, once the codebase is large enough to justify it.
The two-minute self-review before submitting Open metrics.definition.ts — is it the only file naming a canonical status? Open metrics.controller.ts — does the summary handler contain any arithmetic beyond a fold? Run the property test with a deliberately broken timezone and confirm it fails. If all three answer correctly, the submission is sound.
