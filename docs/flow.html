Process & Data Flow

Two paths run through this system. The write path records what each source said, verbatim and fault-isolated. The read path assigns meaning exactly once, through a single SQL function, and derives the summary as a fold over the breakdown so the two views cannot disagree. A third path — CI — makes those guarantees fail the build when they are violated.

1 · System context

Three sources with three shapes and three vocabularies converge into one uniform table. Interpretation is deferred to a single function that both endpoints call.

The one seam Everything left of collected_revenue() is vocabulary-agnostic storage. Everything right of it reads the same number. No code path reaches revenue without passing through that function.

2 · Ingestion — verbatim & fault-isolated

Ingestion never decides what counts as revenue; it records what the source said and quarantines what it can't parse. One malformed record — or one whole source failing — does not sink the batch.

flowchart TD
  R["POST /ingest/run"] --> L{"for each source"}
  L --> F["fetch from source"]
  F --> MAP["mapper → CanonicalTransaction
maps fields · NOT status meaning"]
  MAP --> V{"Zod valid?"}
  V -- yes --> U["upsert · on conflict
(source, external_id) do update"]
  V -- no --> Q[("ingest_quarantine
payload + error")]
  U --> CNT["tally written / updated"]
  Q --> CNT
  CNT --> L
  F -. source throws .-> ERR["record source failure
isolate · continue others"]
  ERR --> L
  L -- all sources done --> SUM["per-source summary:
written · updated · quarantined · failed"]
  • Idempotent: re-running the full ingest leaves the row count unchanged (E2-S4).
  • Verbatim: raw_status is written exactly as received; the mapper touches field names and amounts only, never status meaning.
  • Isolated: Stripe failing does not stop Razorpay or the CSV — the summary reports which source failed and why (E6-S1).
Money trap guarded here Decimal amounts (e.g. legacy 1250.50) are converted to minor units with string/decimal math, never parseFloat(x)*100 — which yields 125049.999… on some inputs and hides the exact class of bug this assignment is about.

3 · Metric read — one definition, applied once

Both endpoints share one controller-validated parameter set, one repository, and one SQL function. The request below is the breakdown; the summary is identical up to the final fold.

sequenceDiagram
  autonumber
  participant C as Client
  participant Ctl as metrics.controller
  participant Repo as metrics.repository
  participant DB as Postgres
  participant Svc as metrics.service
  C->>Ctl: GET /revenue/breakdown (from, to, tz, bucket)
  Ctl->>Ctl: Zod parse · to > from · tz is IANA · bucket in {day,week}
  Ctl->>Repo: getCollectedRevenue(params, COLLECTED_STATUSES)
  Repo->>DB: collected_revenue(from,to,tz,bucket,collected[])
  Note over DB: inner join status_map (allow-list, structural)
half-open [from,to) · date_trunc(bucket, occurred_at at time zone tz)
group by currency · generate_series fills empty buckets
  DB-->>Repo: buckets[] {bucketStart, currency, amount_minor}
  Repo->>DB: unclassified query (left join + null check)
  DB-->>Repo: {count, pairs[]}
  Repo-->>Svc: buckets + unclassified
  Svc->>Svc: summary only → fold buckets into totals per currency
  Svc-->>Ctl: response model
  Ctl-->>C: JSON · echoes applied from,to,tz,bucket + unclassified
  1. Allow-list, structurally. The inner join means an unmapped status cannot match, so it cannot be counted — the allow-list is topology, not an IN (...) that can be edited into an exclusion list.
  2. One timezone, both views. date_trunc(bucket, occurred_at at time zone tz) uses the caller's IANA tz; the same value drives summary and breakdown.
  3. Half-open range. occurred_at >= from and < to — a midnight boundary event is never double-counted across adjacent ranges.
  4. Loud zero. The unclassified count + offending pairs ride in every response, so an unmapped status is visible, not silent.

4 · Why the two views always agree

The summary is not computed beside the breakdown — it is arithmetic performed on it. Two views cannot disagree when one is a pure fold over the other, and a property test proves it on every push.

flowchart LR
  DEF{{"collected_revenue()"}} --> B["breakdown
buckets[] per currency"]
  B -- "Σ per currency
pure fold · no second query" --> S["summary
totals[] per currency"]
  B --> EP1["GET /revenue/breakdown"]
  S --> EP2["GET /revenue/summary"]
  P["E5-S1 reconciliation property test
Σ buckets == totals · strict integer equality"] -. enforces .-> B
  P -. enforces .-> S
Reconciliation by construction fast-check generates ~200 random ranges across years, timezones (Asia/Kolkata, UTC, America/Los_Angeles) and both buckets; for each, the summed breakdown must equal the summary exactly — no tolerance, integers only.

5 · Anti-drift — the mechanism that catches a second implementation

The brief's hardest clause asks for something that would catch a duplicate definition. The answer is CI, not a README note. Four tripwires gate every merge.

flowchart TD
  PUSH["git push / PR"] --> CI["GitHub Actions"]
  CI --> TC["typecheck · tsc"]
  CI --> UT["unit tests"]
  CI --> PT["E5-S1 reconciliation
property test"]
  CI --> MC["E5-S2 mapping coverage
every (source,raw_status) mapped"]
  CI --> SI["E5-S3 single-implementation
grep guard"]
  CI --> EX["E5-S4 exhaustiveness
assertNever"]
  TC & UT & PT & MC & SI & EX --> G{"all green?"}
  G -- yes --> MERGE["merge allowed"]
  G -- no --> BLOCK["build fails · merge blocked"]

The demonstration that lands: three deliberate breakages, three tripwires firing

Breakage introducedTripwire that fires
Seed a new status without a status_map rowE5-S2 mapping coverage — lists the offending pairs
Write a second summary using sum() directly in a routeE5-S3 single-implementation guard — names the file
Bucket the breakdown in UTC while summary uses tzE5-S1 reconciliation — strict-equality mismatch

What E5-S3 actually greps for: the canonical literal collected appears only in metrics.definition.ts; no SQL string in the repo contains a canonical status literal; provider words (succeeded, captured, PAID) appear only in mappers/seed/tests; collected_revenue() is called by exactly one module; and no file outside src/metrics/ contains from transactions in a SQL string.

6 · Build order

The CSV source is built before Stripe — no network, no keys, no rate limits — so the entire metric path can be finished and tested while the live integrations are still unwritten. The tripwires are the grade, so they are scheduled before polish and are never what gets cut.
